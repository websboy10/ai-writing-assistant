# Handoff — Google Docs, 2026-08-17

Written at the end of a session that started as "sign-in is broken" and ended
inside the Docs write path. **Read this before touching anything Docs-related.**
Everything below is either an observation with its evidence, or is labelled as
unverified. Nothing here is reasoning presented as fact — that habit is what
produced the four wrong Docs fixes this file exists to stop repeating.

---

## The one-line state

Sign-in is fixed and live. Google Docs is **not working in either path**, for
two independent reasons, and the single most valuable question about it —
*does the normal product path work?* — has still never been asked.

## 1. Sign-in — FIXED, verified

**Symptom:** every sign-in returned `500 {"error":"Internal Server Error",
"message":"fetch failed"}`.

**Cause:** the Supabase project (`gkqpyqmuopqxumugszoa`) had been auto-paused by
the free tier. A paused project **loses its DNS record** — the hostname went
NXDOMAIN, so every backend `fetch` to GoTrue/PostgREST failed at the network
layer, before any HTTP status existed.

**Fix:** the operator unpaused it. No code changed.

**Verified after the fix:**

| Check | Before | After |
|---|---|---|
| `dig` the Supabase host | NXDOMAIN | resolves |
| `POST /api/auth/login` (bad password) | `500 fetch failed` | `400 invalid_credentials` |
| `/api/conversations` (bad token) | `500` | `401` |

**Diagnose this in one command next time, before reading any code:**

```
dig +short gkqpyqmuopqxumugszoa.supabase.co
```

Two traps worth knowing. `/api/health` returns 200 while the database is gone —
it touches no Supabase, so it is not a liveness check for anything that matters.
And for ~2 minutes after unpausing, the auth proxy passes through Cloudflare's
**521** as `"Auth service returned 521"`; that means still booting, not a new
fault.

**NOT DONE:** nothing keeps the database awake, so this recurs on any quiet
week. Options given to the operator, no decision taken: a scheduled ping every
few days (free), or Supabase Pro (~$25/mo, never pauses). For a live product
with paying users this is a real availability risk, not housekeeping.

## 2. Docs API token — BLOCKED, cause identified, fix unconfirmed

**Symptom:** `P1 — Token (docs-auth)` returns `AFVIST (status 401)` and **no
Google permission prompt ever appears.**

That 401 is ours, not Google's — `docsAuth()` invents it when
`chrome.identity.getAuthToken()` yields no token. The real reason was being
swallowed by a bare `catch`. That is now fixed (see §5), and Chrome's own words
came through:

```
OAuth2 request failed: Service responded with error:
'Service has been disabled for this account.'
```

**What that ruled out**, each on evidence: not our code (the request was
well-formed enough to be answered); not a bad client ID or extension-ID
mismatch (that says `bad client id`); not a Workspace admin policy
(`degirmenci.dk` is not on Workspace — its MX points at simply.com).

**What it is.** Querying Google's authorize endpoint about the client ID in the
manifest returned the client as alive but branded **"Potato App" / "Potatoemail"**
— Google's placeholder for a consent screen nobody configured. The operator
then confirmed: project **508090872713** is called **`my-first-project`**, the
empty default project Google creates for every account.

So the extension has been asking `my-first-project` for document access.
Whether the consent screen, `documents` scope, Docs API and test-user list live
there or in the *AI Skriveassistent* project was **never fully established** —
the operator said "it's in my first project", but the Potato App branding
contradicts that, and the contradiction was never resolved.

**Caveat, so nobody treats this as settled:** the Potato App reading came off an
error page (`redirect_uri_mismatch`, expected — a Chrome-Extension credential
cannot be used in a browser flow). It is a strong signal, not proof.

**Last known state:** the operator added `websboy10@gmail.com` as a test user —
first to one project, later reportedly to `my-first-project` — and the token was
**still refused**. Whether the error string changed after that addition was
asked but never answered. That single fact is the next thing to establish.

### Next steps, in order

1. Re-run the spike's P1 and read **`Chromes egen begrundelse`**. If it still
   says *Service has been disabled for this account*, nothing has moved.
2. If unchanged, run this in the extension's service-worker console
   (`chrome://extensions` → the extension → **service worker**). It asks the
   **same client** for a **harmless basic scope**:

   ```js
   chrome.identity.getAuthToken({ interactive: true, scopes: ['https://www.googleapis.com/auth/userinfo.email'] })
     .then(t => console.log('OK:', !!t)).catch(e => console.log('FEJL:', e.message));
   ```

   - **Also refused** → the client or its project is the problem, not the scope
     or the test list. Consolidate: pick ONE project, ensure it has the consent
     screen, the `documents` scope, the Docs API, the test user, **and** the
     Chrome Extension client, then put that client ID in `wxt.config.ts`.
   - **Prompts and succeeds** → the sensitive `documents` scope is the blocker,
     and the test-user/consent-screen trail is the right one.

3. `websboy10@gmail.com` must also be able to **open the test document**, or the
   next error will be a 403/404 with our "har ikke adgang til dette dokument"
   message. That is progress, not a regression.

### The strategic question nobody has answered

`chrome.identity.getAuthToken()` can only ever use the account **Chrome itself
is signed into** — no account picker, no user recourse. The first demand signal
for this product is **HR teams**, who are overwhelmingly on Google Workspace,
where an admin can disable exactly this. When they do, the user gets no prompt,
no explanation, and a silent degrade to paste.

`chrome.identity.launchWebAuthFlow` (already used for Supabase sign-in,
`background.ts:306`) lets the user pick any account and ignores the Chrome
profile — but needs a Web-application client and token refresh we would own.
**This was put to the operator and not decided.** It should be decided
deliberately, not discovered from a customer.

## 3. Whitespace on Docs — root cause CONFIRMED, fix not yet determined

**Symptom (long-standing):** slow-typed text lands as `detterikke` — letters
arrive, the spaces between them do not.

**Confirmed 2026-08-17 by running the probe against a real document:**

| Variant | Written as | Landed | Spaces |
|---|---|---|---|
| A | one paste `A B C` | `A B C` | kept |
| B | `A`, `' B'`, `' C'` (what Langsomt does today) | `ABC` | lost |
| C | `A`, `' '`, `B`, `' '`, `C` | `ABC` | lost |

Observed document content: `A B CABCABC`.

**Root cause: Docs trims each individual paste.** Whitespace at the edge of a
paste is discarded; only whitespace *interior* to a single paste survives.
Against the interpretation table fixed in advance (F-4 of `07-FINDINGS-docs.md`)
this is the row *"chunk Docs at word level; do not touch the engine."*

**Why the fix is not written yet.** B and C both put the space at the **front**
of a chunk. Nothing has tested the **end**. That detail decides the size of the
fix, and guessing it is exactly the failure mode this phase keeps repeating:

- trims only the front → chunks like `'A '`, `'B '`, `'C'` work; a few lines in
  the Docs chunker, ordinary characters, done
- trims both ends → **no** chunk-by-chunk scheme can put a space between two
  pastes, and Langsomt on Docs needs a different strategy (larger pieces, or a
  single write as `GDocsApiWriteSource` already does)

**Three variants are BUILT and NOT YET RUN** (`content/index.tsx`, distinct
letters per variant because the markers do not survive the write):

| Part | Written as | If it keeps its spaces |
|---|---|---|
| `D E F` | ordinary space at the **end** | only the front is trimmed — small fix |
| `G H I` | non-breaking space at the **end** | NBSP survives trimming |
| `J K L` | non-breaking space at the **front** | NBSP survives on the front |

If only an NBSP variant survives, that is a **compromise needing an operator
decision**: documents would receive non-breaking spaces, which look identical
but behave differently for line-wrapping, search and copy-out.

**To run it:** delete the old probe text from the document → reload the
extension → **Cmd+R the Docs tab** → run the probe from
`chrome-extension://foidkbeinmfolejjjfjcokmmknimohof/spike.html` → copy the
document text out and inspect the **actual characters** (an eye cannot tell an
NBSP from a space; the API read-back is still blocked by §2).

## 4. The focus gate — new, and it invalidated two earlier runs

**Docs silently discards a synthetic paste when its hidden input frame does not
have keyboard focus.** Every success signal still reads fine: correct target,
`notCancelled: true`, no exception. Nothing lands.

Measured: in one run chunks 0–4 logged `docHasFocus: false` and vanished;
chunks 5–11 logged `true` (the operator had clicked into the document mid-run)
and survived. Nothing else varied — same element, same iframe, contenteditable,
never `body`.

This matters beyond the probe:

- **`notCancelled: true` is not a success signal and must never be read as one.**
  Docs consumes a paste without calling `preventDefault`. The adapter cannot
  verify its own writes (canvas). "Skrevet" in the spike meant only "dispatched".
- The probe is driven from the spike page **in another tab**, so an unfocused
  document was its *default* state, not an edge case. Two runs' worth of data
  were invalid and one of them was nearly read as evidence about trimming.

**Fixed** (§5): the probe now polls for real focus before writing, re-checks
**before every chunk**, aborts with a plain-Danish reason instead of reporting
success, and brings the document to the front itself rather than hoping.

**Still unexplained, flagged not solved:** the `\n⟪AWA-SP-x⟫` marker chunks do
not survive the write even with focus, while the letter chunks do. Leading-`\n`
trimming would still leave the marker text visible. Nobody has investigated
this. It may be the same trimming rule or something else; do not assume.

## 6. The question that has never been asked

**Does Google Docs insertion work on the normal product path?**

Every failure this session came through the spike page, which drives the
document **from another tab**. The sidebar runs **inside** the Docs tab, driven
by a real click. Those differ in at least two ways that are known to matter to
Docs: focus (now proven) and user activation (suspected, untested).

The test is one minute: cursor in the document → open the sidebar → ask for a
sentence → insert with **Straks** → does text appear?

- **Yes** → the product is healthier than this session suggests, and the
  remaining Docs work is the whitespace chunker plus the token.
- **No** → the synthetic-paste mechanism is gone, and that is an architectural
  decision for the operator (Docs API only, a different mechanism, or telling
  users to paste manually on Docs) — **not** a fifth reasoned fix to the adapter.

It was proposed three times this session and never run. **Run it first next
session.** It costs a minute and it changes what everything else is worth.
