<objective>
Google Docs, built properly rather than worked around — the reason this phase exists.

The shape, locked in D-16 after research showed an API-per-letter Langsomt is
quota-impossible:

1. **Read** with `documents.get` — one request per run. It yields every question, its
   exact text and its index, and it hands us headings, tables and list items as
   *structure* rather than a wall of text, which makes question detection materially
   better.
2. **Position** with Docs' own **Find**, which is real DOM even though the page is a
   canvas, fed the exact question text from step 1.
3. **Type** with the `InsertionSession` and `GDocsAdapter` that already exist. Local,
   unlimited, no write quota.

Cost: one read request, zero writes. True letter-by-letter, in place, top to bottom.

Purpose: this is the only remaining path where the product's core promise — text landing
where the user is already working — is not yet delivered, and it is where the first real
demand signal lives (HR teams writing reviews in Google Docs).
Output: three Docs sources and a resolver that downgrades visibly rather than silently.

**Read `07-SPIKE.md` first.** On `VERDICT: NO-GO`, task 2 is not executed — record it as
skipped with the verdict as the reason, and Docs runs on task 3's `batchUpdate` path.
Task 3 is built either way: it is D-06's fallback, not a consolation prize.
</objective>

`readDocsParagraphs()`: extract the document id from `location.href`; send `docs-get`;
map each `DocsParagraph` to an `AutonomousParagraph` whose `index` is the array position,
keeping the `startIndex`/`endIndex` in a parallel private array the sources use later.
Skip empty paragraphs but never renumber the kept ones after the fact — the index the
model receives must be the index the source can resolve.

`resolveDocsSource(scope)`: pick the source in this order, and make every downgrade
visible by returning it in `degradedReason`:
1. `GDocsAdapter.selfTest()` fails → `GDocsPasteSource` cannot work either; return an
   error, not a source. The user gets the existing INST-13 message and copy-to-clipboard.
2. `docs-auth` with `interactive: true` returns granted → the API sources are available.
   Ask for the permission at this moment, not at sign-in: this is the first time it is
   actually needed, and incremental consent is materially better than demanding it up
   front.
3. Not granted, or `docs-get` fails → `GDocsPasteSource` with `placement: 'block'` and a
   plain-Danish `degradedReason` explaining that without the Google permission the
   answers are collected in one block at the cursor with each question repeated above
   its answer, and how to grant it if they change their mind (D-02, D-06).
4. Granted → `GDocsFindSource` when `07-SPIKE.md` says GO, otherwise
   `GDocsApiWriteSource`. Both are `placement: 'in-place'`; `GDocsApiWriteSource` carries
   a `degradedReason` only for the Langsomt case, set in task 3.

`GDocsPasteSource`: `read()` cannot use the API, so it uses what today's mechanism can
see — the marked selection via the hidden mirror for `scope: 'selection'`; for
`scope: 'document'` it must say honestly that it cannot read the document without the
Google permission and return empty, so the panel shows a specific message rather than an
empty run. `locate()` always returns the current cursor target — the block placement is
handled by task 3's composition.

Wire `sourceFor` in `locator.ts` to dispatch `kind === 'gdocs'` to `resolveDocsSource`,

Never request more than the `documents` scope. Never send the document text anywhere

Implement `GDocsFindSource`:
- `read()` → `readDocsParagraphs()`.
- `locate(q)` → call `findAndPlaceCursor(q.questionText)`. On success return a
  `SavedTarget` of kind `'gdocs'` whose element is `gdocsEventTarget()`, so the
  orchestrator's existing `adapterFor` produces a `GDocsAdapter` and the existing session
  types the answer letter by letter at the cursor Find just placed.
  `GDocsAdapter.prepare()` already collapses a selection to its end — that is exactly the
  state Find leaves behind, and the two fit together without modification. Do not add a
  second collapse.
- On a `findAndPlaceCursor` failure, return `null` with the reason, so the orchestrator
  reports that question as unplaced and carries on. Never fall through to "type at
  wherever the cursor happens to be" — that would write an answer into the middle of the
  user's sentence.

Harden `docs-find.ts` for production use:
- Questions longer than Docs' find field: search on the first 60 characters and, if that
  yields no selection, fall back to the first sentence. Both attempts must still end in
  a `hasSelection()` confirmation.
- Two questions with identical text: Find lands on the first. After each answer is
  written, advance Find's internal position by pressing Enter again before Escape for the
  n-th duplicate, and track a per-run occurrence counter so the second identical question
  gets the second occurrence.
- Always dispatch Escape to close the find bar, including on every failure path — leaving
  Docs' find bar open would break the user's next keystroke.
- Re-run `findAndPlaceCursor` for each question at the moment it is needed. The document
  grows as answers land, and D-03 forbids positions measured up front.

**`GDocsApiWriteSource`** — used when the token is granted but Find is not the mechanism
(NO-GO verdict, or a runtime find failure rate that makes it unusable):
- Straks stays **in place**. Insert every answer with `docs-batch-update`, processing
  questions in `orderForRun(answers, 'bottom-up')` — highest index first. Inserting at a
  higher index never shifts the indices above it, so each remaining question's captured
  `endIndex` stays valid without a re-read. This is Google's own documented ordering rule
  and it is the one place in this phase where bottom-up is correct.
- Langsomt on this source cannot be letter-by-letter — 30 wpm needs about 150 writes a
  minute against a 60-per-minute cap. Set `placement: 'block'` and a `degradedReason`
  stating plainly that on Google Docs without the Find mechanism the slow mode would hit
  Google's limit, so the answers are written at once instead. Do not invent a buffered
  pseudo-typing mode: the operator rejected compromises on what Langsomt looks like, and a
  bursty fake is worse than an honest instant write.
- Undo is exact here: keep each inserted range and delete them in the same bottom-up
  order with a second `docs-batch-update`. Report a partial failure honestly.

**`GDocsPasteSource` composition (D-02)** — no token, no API:
- Compose one block: for each question, the question text repeated, then its answer

  existing `GDocsAdapter` at the current cursor, so Straks and Langsomt both still behave
  as they do everywhere else.

- Undo stays best-effort (one synthetic undo per chunk) and the panel says so — the same
  honesty the existing adapter already practices.

**Orchestrator**: when `source.placement === 'block'`, skip per-question location entirely

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| extension → docs.googleapis.com | Authenticated read and, on the fallback, write access to a real document |
| Google Docs page → extension | Document content is untrusted and is sent to the model |
| user consent → capability | What the user granted decides what runs |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-19 | Elevation of Privilege | Write access to a real document with no review step | mitigate | The only Docs write ever issued is `insertText`. No `deleteContentRange` except against ranges this run itself created during undo, no permission or sharing call, no Drive-wide API, and the OAuth scope stays exactly `documents`. |
| T-07-20 | Tampering | An answer typed at the wrong place after a failed Find | mitigate | `locate()` returns null on any find failure and the question is reported as unplaced; it never falls through to the current cursor. `GDocsAdapter.insert` already reports a refused paste as a failure rather than a silent success. |
| T-07-21 | Information Disclosure | Google token leaking into the page or a log | mitigate | The token stays in the background service worker (07-01); this plan's code only ever sends `docs-*` messages and receives results. |
| T-07-22 | Spoofing | The Chrome profile's Google account differs from the one that can open the document | mitigate | 403/404 from `docs-get` produces a specific message naming the situation, and the resolver downgrades to the visible paste fallback rather than presenting an empty run. |
| T-07-23 | Denial of Service | Docs write quota (60/min/user) on the fallback path | mitigate | The primary path issues zero writes. The fallback issues one `batchUpdate` per answer for Straks only; Langsomt on that source is explicitly not letter-by-letter, which is why the block degradation exists rather than a buffered fake. A 429 surfaces as the specific message added in 07-01. |
| T-07-SC | Tampering | npm/pip/cargo installs | mitigate | No package-manager install occurs. The Docs API is reached with `fetch` and the token with `chrome.identity`, both already present. |
</threat_model>
