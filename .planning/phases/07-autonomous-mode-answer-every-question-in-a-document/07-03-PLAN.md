<objective>
The engine, and the first entry point: a button that answers every question in the
document you are looking at.

This plan is where "one capability, two entry points" is decided. The orchestrator takes
a *source* (whatever holds the questions) and a list of answers, and drives the existing
`InsertionSession` once per answer. Nothing in it knows whether the questions came from a
whole document or a marked selection, or whether the editor is a textarea, a rich-text
editor or Google Docs. That is what stops this becoming two systems.

Purpose: prove the run works on the two editors we can test automatically, before the
Google Docs path is layered on in 07-05.
Output: the ordering rules, the source/locator abstraction, the run orchestrator, a
minimal button, and a real-browser test that fails before the feature exists.

**Deliberately not in this plan:** the Straks/Langsomt prompt on "Besvar markeringen",
the gap list, the run transport bar, and anything Google Docs. Those are 07-04 and 07-05.
</objective>

  <action>
Three modules, in this order.

**`plan.ts`** — pure, no DOM. Export `orderForRun(answers, direction)` and
`orderForUndo(completed)`. `direction` is `'top-down'` or `'bottom-up'`, sorting by
`paragraphIndex` ascending or descending, stable for ties. Default and only value used
in this plan is `'top-down'`: D-04 requires Langsomt to start at the first question and
work downward, and users watch it. `'bottom-up'` exists for one caller only — the Google
Docs `batchUpdate` fallback in 07-05, where descending order keeps earlier indices valid.
`orderForUndo` returns the completed items in the reverse of the order they were
inserted, so removing a later answer never invalidates an earlier one's offsets.

**`locator.ts`** — export:
`interface QuestionSource { readonly kind: EditorKind; readonly label: string; readonly placement: 'in-place' | 'block'; readonly degradedReason?: string; read(): Promise<AutonomousParagraph[]>; locate(q: { paragraphIndex: number; questionText: string }): Promise<SavedTarget | null> }`
and `function sourceFor(target: SavedTarget, scope: 'document' | 'selection'): QuestionSource`.

`DomSource` implements it for `plain` and `contenteditable`:
- `read()` for plain splits the field value on newlines; for contenteditable it walks the
  editor's block elements (p, div, li, h1-h6) and takes each block's textContent. Blank
  entries are skipped. `index` is the position in the emitted array. When `scope` is
  `'selection'`, restrict to the captured selection range — for plain, the substring
  between `selStart` and `selEnd`; for contenteditable, the blocks the saved Range
  intersects.
- `locate()` searches the CURRENT content for `questionText`, starting after the end of
  the previously located question, and returns a SavedTarget whose caret sits at the end
  of that question's line/block: for plain, set `selectionStart`/`selectionEnd` on the
  element to that offset and return a target carrying it (PlainAdapter.prepare reads
  `selectionEnd`); for contenteditable, build a Range collapsed at the end of that block
  and return it as `target.range`. A match that is absent, or ambiguous within the
  remaining region, returns `null` — never a guess. This is the same "re-anchor or
  refuse" rule `PlainAdapter.locateInserted` already applies, and it is what makes D-03
  safe: positions are resolved one at a time, against the document as it is now.
- `placement` is `'in-place'` for both DOM kinds.

**`orchestrator.ts`** — export `class AutonomousRun`:
`constructor(source: QuestionSource, answers: AutonomousAnswer[], mode: 'instant' | 'progressive', cb: RunCallbacks)`
and `start(): Promise<void>`, `pause()`, `resume()`, `stop()`, `undo(): { ok: boolean; reason?: string }`, `destroy()`.
Export `type RunState = 'idle' | 'writing' | 'paused' | 'stopped' | 'done' | 'error'` and
`interface RunCallbacks { onRunState(state: RunState, detail?: string): void; onProgress(p: { answersDone: number; answersTotal: number; charsInAnswer: number; charsTotal: number }): void; onUnplaced(q: { questionText: string; reason: string }): void }`.

Rules:
- Iterate `orderForRun(answers, 'top-down')`. For each answer, call `source.locate()`
  **at that moment** — never resolve all positions up front (D-03).
- `locate()` returning null: report through `onUnplaced` with a specific reason and
  continue with the next question. One unfindable question must not abandon the rest.
- Build the adapter with the existing `adapterFor(target)` and one `new InsertionSession`
  per answer, text prefixed with a newline so the answer lands on the line below its
  question and never replaces it.
- Straks calls `insertInstant()`; Langsomt calls `start()` and waits for that session to
  reach `done` before locating the next question.
- The per-session typing-race guard is reused untouched. When a session reports
  `paused` with detail `user-typing`, the whole run enters `paused` — the user typed, so
  nothing else starts until they resume (D-13).
- `pause`/`resume`/`stop` forward to the current session and hold the queue.
- `undo()` walks `orderForUndo(completed)` calling each session's `undo()`, aggregating
  failures into one reason string. It is one user-visible step across the whole run
  (D-15). Report honestly which answers could not be removed rather than claiming success.
- Keep every session object alive until the run is dismissed — undo needs them.

Export `AutonomousRun`, `sourceFor` and the run types from
`apps/extension/insertion/index.ts` alongside the existing exports.

Do not add a pacing control, a mode preference, or any setting. Two modes, hardcoded.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host page DOM → extension | Document text is untrusted input and is sent to the model |
| model answers → host page DOM | Generated text is written into the user's document with no review step |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-11 | Tampering | Answer written at the wrong position | mitigate | `locate()` requires a unique match of the question's verbatim text in the current content and returns null otherwise; the orchestrator reports the question through `onUnplaced` instead of writing. Positions are resolved one at a time (D-03), never measured up front. |
| T-07-12 | Tampering | Prompt injection from document content, with no review step (D-04) | accept | Bounded by construction: the run can only insert plain text at located question ends and can only undo its own insertions. It cannot delete arbitrary ranges, and it holds no credentials. The operator accepted the fabrication risk explicitly (ROADMAP "Operator-accepted risk"); D-11 and D-12 are the mitigation that fits inside that decision. |
| T-07-13 | Tampering | User types mid-run and the run writes over them | mitigate | The existing INST-12 typing-race guard is reused unmodified; a trusted keystroke pauses the whole run (D-13). `InsertionSession.resume()` re-verifies before continuing and fails loudly if the text moved. |
| T-07-14 | Denial of Service | A very long document sent from the client | mitigate | The backend's `MAX_AUTONOMOUS_DOC_CHARS` rejection surfaces here as a specific message telling the user to mark a section instead. |
| T-07-SC | Tampering | npm/pip/cargo installs | mitigate | No package-manager install occurs in this plan. |
</threat_model>
